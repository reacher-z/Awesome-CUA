Evaluation, interaction data, and safety

A computer-use benchmark measures an agent under a particular observation interface, action interface, task population, initial state, execution budget, and scoring procedure. A screenshot-to-coordinate test measures something different from selecting an element already identified in an accessibility tree. Likewise, predicting the next recorded action differs from completing a task after the agent has changed the environment. Here, interactive evaluation means that executed actions produce subsequent observations; it does not require a live Internet connection or a conversation with a human. A locally hosted website can support interactive evaluation, whereas a Gym-compatible wrapper can expose a single offline prediction problem. BrowserGym makes this distinction concrete by accommodating both executable web tasks and recorded WebLINX action prediction.

These distinctions prevent a defensible universal leaderboard across the resources below. Even within a named benchmark, a changed evaluator, task subset, action budget, or permitted interface changes the experiment. The original World of Bits describes 100 authored MiniWoB environments, while the workflow-guided exploration study selects 40 of 80 then-public tasks for its action space and disables partial rewards. These are different historical populations and protocols, rather than inconsistent measurements of one immutable test set.

Environments and scoring contracts

Executable environments move evaluation beyond matching a demonstration. WebArena checks answers, navigation, and changes to website state; OSWorld checks artifacts, settings, and other task-specific outputs after execution. This allows different successful trajectories to receive credit. Functional verdicts range from exact, deterministic comparisons to model-based judgments: WebArena includes language-model semantic matching; VisualWebArena adds visual question answering (VQA) and image-similarity checks. Evaluator implementation and judge versions therefore belong in the experimental specification alongside the policy model.

The interface also supplies information and authority. WorkArena can expose element identifiers, coordinates and action-error messages; Windows Agent Arena supports clipboard and window metadata as well as screenshots. AndroidWorld includes limited function-calling options beyond gestures. These are legitimate experimental configurations, but each changes what the agent must infer or execute. A comparison between backbones is therefore interpretable only after aligning the surrounding agent configuration. Conversely, an interface ablation can deliberately vary those capabilities, provided the change is identified as part of the intervention rather than attributed entirely to the underlying model.

State control is part of the measurement, not merely deployment plumbing. BrowserGym documents backend restoration and dependencies that prevent one agent’s modifications from corrupting another run. WorkArena++ uses separate task accounts to isolate state changes. AndroidWorld fixes application versions and the device clock as well as task parameters. In contrast, AssistantBench deliberately uses the open web, selecting comparatively stable answers without eliminating future content changes. These choices trade environmental breadth against control; neither setting alone establishes performance across the other.

Stopping has its own semantics. WebArena includes requests that cannot be fulfilled because necessary evidence, permissions or functionality are absent; VisualWebArena evaluates explanations of unachievable tasks. WorkArena++ also distinguishes declaring infeasibility from justifying it. Thus a successful episode need not end in the requested state change: correctly recognizing an impossible request can itself be the desired outcome. This differs from refusing a feasible but unsafe request. Aggregate results should preserve that distinction, since an agent that stops, answers, requests clarification or changes state may receive superficially similar labels for substantially different reasons.

Interaction data and the limits of offline proxies

Offline corpora provide reproducible observations and labels at a much lower execution cost, but their scores answer narrower questions. Mind2Web supplies the correct action history when scoring each step; its task score requires all recorded steps to match. AITW explicitly compares action matching with human online judgments and notes that alternative successful actions can be rejected by the offline matcher. AndroidControl likewise acknowledges that offline evaluation does not reward alternative routes or corrective behavior. Consequently, an all-steps-correct trace score should not be relabeled as independently observed end-to-end task completion.

Instruction granularity also changes the inference problem. AndroidControl distinguishes high-level goals from prompts that additionally supply the next low-level instruction. GUIOdyssey separately evaluates these settings and tests cross-app histories. Supplying the next instruction removes part of the planning burden, so the resulting score cannot be interpreted as equivalent autonomous competence. Grounding-only sets provide a useful complementary diagnosis: ScreenSpot isolates target localization, while ScreenSpot-Pro stresses small targets in professional high-resolution interfaces. Strong localization is relevant to successful control, but neither benchmark directly tests recovery, stopping, or side effects.

GUIOdyssey pairs human demonstrations with model-generated low-level instructions and semantic annotations. These annotations are training products rather than observations of a demonstrator’s internal reasoning. The methods section discusses the analogous distinction for OpenCUA.

Reference traces and recovery data answer different questions. As discussed under memory and recovery, a useful recovery example must identify the mistaken state, corrective action and observed result. A clean all-correct sequence cannot by itself establish competence on those off-path states.

Generalization, efficiency, and uncertainty

Generalization needs a declared axis. Mind2Web separates unseen tasks, websites and domains; AndroidControl tests unseen apps, tasks and categories; GUIOdyssey adds device transfer. These partitions probe different shifts and should retain their original membership rules. In particular, AndroidControl explicitly allows overlapping held-out subsets. AITW’s limitations further identify English-only prompts, a restricted annotator population, and mouse/keyboard interaction with emulated phones. More recorded episodes therefore do not, by themselves, establish broader linguistic, demographic or physical-interaction coverage.

Train/test separation is necessary but does not certify independence from all earlier training. OpenCUA reports avoiding OSWorld task overlap; OS-Harm requests exclusion from training and supplies a canary marker. These are documented safeguards, not an independent audit of every foundation model’s pretraining corpus. We therefore distinguish known task overlap, benchmark-specific tuning, and unknown pretraining exposure. A related issue is environmental overfitting: AndroidReality perturbs AndroidWorld’s observations, transitions and action execution while preserving task goals and rewards. Its predominantly single-perturbation protocol tests controlled robustness, rather than arbitrary combinations of deployment failures.

Uncertainty also depends on the sampling unit. Steps within a demonstration, variants of an instruction template, and repeated seeds of the same task should not be described as unrelated tasks. WorkArena++ deliberately reuses workflows under different instruction levels, while AndroidWorld’s robustness analysis observes variation across parameter seeds. DIBench explicitly pairs benign and injected runs using matched seeds. These designs support different comparisons: transfer across task families, sensitivity to initial conditions, or a controlled change at a decision point. Reports should identify which population an average describes before attaching an uncertainty interval or claiming a general improvement.

Efficiency cannot be reduced to a step count without defining a step. A single call may issue several operations, and a grouped action may avoid another screenshot or model request. OSWorld-Human provides both single-action and grouped human reference trajectories and proposes success-weighted efficiency with a failure-budget penalty. That metric complements, rather than replaces, elapsed time, model calls, tokens and monetary cost. Comparisons should disclose what is charged for retries, failed attempts, parsing repair and environment recovery; otherwise two agents with the same success score may have substantially different operational costs.

Human reference trajectories also encode choices about permitted tools. OSWorld-Human generally excludes programmatic application-specific solutions unless the task source calls for them, while allowing familiar keyboard shortcuts. Its reference is consequently a documented human interaction procedure, not a proven shortest path through every possible computer interface. Normalization against that reference should retain these assumptions, especially when an agent is allowed code, macros or multiple actions per observation.

Evaluators require their own validation. OSWorld-Pro compares step-, subgoal- and task-level model judgments with human trajectory labels. A recent WebArena-Lite audit retains original and human-corrected outcomes, while explicitly limiting its conclusions because it uses one rollout per task and identifies possible state carryover and guidance leakage. These studies motivate trace inspection and human-checked judges, not treating human correction as infallible. AndroidControl-Curated proposes revised grounding and task annotations, but its exact-point comparison should not be generalized to the original AndroidControl paper, which already describes relaxed action equivalence. Improvements under changed scoring rules must be separated from policy improvements.

Safety beyond nominal task completion

A correctly completed task can still be unsafe. OSWorld’s original discussion acknowledges that its completion checks do not comprehensively detect unnecessary harmful side effects. OS-Harm separates deliberate user misuse, indirect prompt injection and harmful model behavior during otherwise benign tasks. MobileSafetyBench instead makes the utility–safety distinction visible through low-risk completion and high-risk refusal or consent requests. Refusing every request can suppress realized harm while providing little useful assistance; failing to carry out a harmful instruction can also reflect insufficient capability rather than a reliable boundary.

Indirect-injection results are meaningful only relative to attacker control. WASP restricts the adversary to user-editable website content. The VisualWebArena adversarial-robustness study considers restricted text or image modifications and analyzes how compromised observations propagate through agent components. RedTeamCUA extends testing into a hybrid web–desktop sandbox while retaining explicit restrictions on what the attacker may change. These differ from malicious-user requests and from attacks that assume control of the policy itself. Their rates should not be pooled into a single measure of “agent security.”

Exposure and completion are separate denominators. VWA-Adv starts agents at an attack encounter; RedTeamCUA distinguishes this decoupled setting from end-to-end navigation. Such trials isolate susceptibility after exposure, whereas end-to-end trials additionally depend on reaching the relevant state. WASP reports intermediate diversion separately from completed attacker goals, and RedTeamCUA distinguishes attempted from executed harmful behavior. Together, these designs show why evaluation should retain benign utility, exposure, deviation and completed harm as separate outcomes. A navigation failure is not evidence that encountered malicious content would be resisted.

Decision integrity adds another boundary. DIBench holds the instruction and candidate set fixed while comparing benign and injected selection states. Its completion metric means committing to a candidate; correctness means selecting an acceptable candidate; targeted steering is measured through paired choices. Commercial-app tests use fixed screenshots and context, rather than publishing malicious content or executing transactions. The study therefore supports analysis of manipulated choices even when the interaction appears orderly, but does not establish end-to-end transaction safety or the behavior of production phone assistants.

Other threats enter at different stages. The third-party mobile-agent study (A)I Sees What You Don’t assumes an installed malicious Android application and examines perception and automation-channel boundaries, with permission requirements varying by vector. Its controlled feasibility demonstrations do not estimate attack prevalence or directly transfer to first-party and iOS assistants. Poison Once, Control Anywhere instead assumes compromised visual fine-tuning data. Its target-action and contextual-output measurements concern a training-time backdoor, not the same runtime-injection experiment. Distinguishing these assumptions identifies which component, interface or data pipeline a defense must protect.

Safety judges are themselves part of the evaluated system. OS-Harm uses semantic trajectory judgments and explicitly assumes the adversary targets the agent rather than the judge. SafeMobile combines a trajectory-aware guard with automated scoring and human comparisons; its score threshold is a particular judging rule, not a universal scale of risk. Reporting human agreement, disagreements, the evidence available to the judge and changes in benign task completion is therefore essential when interpreting a defense. No result here demonstrates a universally secure computer-use agent.

Reporting recommendations

The following are recommendations from this synthesis, rather than additional experimental findings. First, publish an evaluation contract: task IDs and version; split and sampling unit; observation/action restrictions; environment image, app versions and reset procedure; model snapshot; step and time budgets; seeds; retry policy; and evaluator code or judge configuration. Preserve raw outcomes alongside corrected outcomes and state the correction rules. Report repeated trials where feasible and identify infrastructure failures separately, without silently deleting them from the denominator.

Second, retain enough execution evidence to inspect the conclusion: task instruction, observations, actions, action results, relevant final artifacts and termination reason. Separate grounding, planning, execution, recovery and stopping failures. Report success together with latency and resource consumption, then stratify by meaningful shifts such as unseen applications, task families and devices. For security evaluation, additionally declare attacker permissions, exposure conditions, allowed channels and the definitions of attempted and completed harm.

Finally, document access and licensing by component. Benchmark code, task instructions and screenshots, model weights, and the applications needed for execution can have different terms. Windows Agent Arena explicitly distinguishes its open implementation from the Windows image it cannot redistribute; ScreenSpot-Pro cites professional-software licensing constraints when limiting its scope to grounding. A public repository is consequently not evidence of unrestricted rights to every associated artifact. Report verified terms separately, leave unknown terms unresolved, and distinguish paper-reported collection sizes from the actual version of data made available.
