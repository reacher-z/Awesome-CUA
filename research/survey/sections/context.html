Scope, historical foundations, and relation to prior surveys

Computer use as interaction with software

Computer-use agents connect a user's goal to changes in software. Their distinguishing problem is not simply producing an answer about an interface: they must select and execute actions, observe what happened, and continue toward the goal. We use computer-use agent for a system that carries out tasks in a software environment through an observation–action loop. Within that broader category, this survey centers on graphical user interfaces (GUIs) on web, desktop, and mobile platforms, together with the representations and infrastructure that make those interactions possible. This operational definition follows the agent–environment perspective developed by Sager et al. and the environment, observation, and action distinctions used in the OS-agent survey. It does not require a particular model architecture or unrestricted autonomy.

An interface is more than its pixels. A browser agent may observe a screenshot, the document object model (DOM), an accessibility tree, or a combination of these. A desktop agent may also need information about open windows and files; a mobile agent must translate decisions into touches, gestures, and navigation operations. Consequently, a screenshot-only definition would exclude substantial interface research. Conversely, generic tool calling is not sufficient evidence of computer use within our scope. A method belongs in the central discussion when it performs software-interface actions or provides a concrete component for understanding, grounding, or evaluating those actions. Hybrid systems that combine interface operations with code or application programming interfaces (APIs) are relevant when that relationship is documented. Zhang et al. explicitly discuss this combination, rather than treating GUI and API execution as mutually exclusive designs.

This boundary also separates an enabling capability from a complete agent. Recognizing a button, describing a screen, predicting a demonstrated next action, and accomplishing a task in a changing application are related but distinct achievements. Pix2Struct, for example, evaluates interface understanding through referring-expression selection and screen or widget captioning; those experiments support its relevance to perception, without establishing autonomous task completion. A paper about physical navigation, a generic language-only planner, or a document question-answering model is not brought into the core merely because its techniques might transfer. The same distinction applies to autonomy: asking for clarification, yielding control, or requiring confirmation can be part of a useful agent's behavior.

Several historical threads, rather than one succession

The motivation to automate interfaces predates foundation models. Koala, published in 2007, recorded browser interactions as editable, approximately natural-language instructions and shared them through a wiki. It combined demonstration, contextual interpretation of page elements, and personalization through user data. Its worked example also included steps left to the user and mechanisms for correcting an interpretation. Sikuli's 2009 institutional abstract describes a complementary approach: screenshots could identify interface elements for search and serve as patterns in scripts that direct mouse and keyboard events. These works established different ways to connect a user's recognizable interface to executable behavior. They should not be retrospectively described as general-purpose language-model agents.

Mobile research developed both task automation and reusable interface corpora. SUGILITE combined verbal commands, user demonstrations, and Android accessibility hierarchies to generalize recorded procedures, including procedures spanning applications. The paper describes context checks and error handling, but also limitations of its string-based generalization and accessibility-dependent implementation. Rico addressed a different need: it combined human and automated exploration of Android applications to collect screenshots, view hierarchies, interaction traces, and interface representations for data-driven design applications. Rico is therefore an important interface-data resource, not evidence that an autonomous agent had mastered those applications. Keeping the original paper, its collected data, and later distributions distinct avoids transferring claims between different releases.

A parallel thread made web interaction an environment for learning. World of Bits exposed rendered pixels and DOM information, accepted keyboard and mouse operations, and addressed the difficulty of obtaining rewards while reproducing changing websites. Its settings included small controlled tasks in MiniWoB and approximations of websites reconstructed from recorded HTTP traffic. Workflow-Guided Exploration subsequently used demonstrations to constrain exploration and trained a separate policy from successful experience. That work also introduced MiniWoB++ tasks involving additional language, layout, and horizon challenges. MiniWoB and MiniWoB++ are related contributions, but the later extension should not be silently attributed to the original platform paper.

Interface representation and behavioral data remained distinct routes toward broader capability. Pix2Struct pretrained an image-to-text model to recover simplified HTML from masked webpage screenshots, then adapted it to visually situated language tasks, including mobile-interface understanding. Android in the Wild collected natural-language goals and demonstrations containing screenshots, typed text, navigation actions, and coordinate-based gestures across Android versions and device configurations. The former supplies a representation-learning approach; the latter supplies demonstrated behavior and generalization settings. Neither resource alone establishes how reliably an agent will recover after its own erroneous action. Android in the Wild explicitly distinguishes its reproducible offline action-matching evaluation from more costly online validation.

Language-conditioned web tasks broadened the relationship between instructions and software state. WebShop introduced a simulated shopping environment built from real product information, with search and selection actions and a reward tied to the requested product properties. Its reported model experiments used a simplified observation mode; its preliminary transfer experiment permitted real-site navigation while retaining consequential form actions inside the evaluation interface. Mind2Web instead recorded tasks and interaction traces from real websites, including webpage snapshots, to study generalization across tasks, websites, and domains. Its authors acknowledge that evaluation against cached actions can reject valid alternative paths. These are different experimental contracts, even when both are described as web-agent research.

Interactive environments then made task outcomes a more direct object of study. WebArena supplied standalone, functional websites and task-specific checks, allowing agents to produce states beyond a single recorded trajectory. OSWorld extended this emphasis to real desktop applications, files, and workflows involving multiple applications within controlled operating-system environments. AndroidWorld constructed parameterized tasks in an Android emulator, with initialization, success checking, and cleanup tied to application or system state. These environments support different forms of repeatable interaction; they do not make every deployment condition identical. WebArena deliberately controls its websites, OSWorld's benchmark and infrastructure have distinct platform coverage, and AndroidWorld fixes operating-system and application versions for reproducibility.

The history thus contains overlapping lines of work: end-user automation, interface representation, demonstration collection, policy learning, and executable evaluation. Foundation models connect these lines through flexible language and visual processing, but the earlier questions remain recognizable: what does an instruction mean in the current interface, which information is observable, when should a procedure adapt, and what counts as completion? Shared scripts and demonstrations remain useful even when an agent can plan; structured interface access remains useful even when it can see. This continuity motivates a survey organized around relationships among capabilities and evidence, rather than a chronology that assumes each new method replaces its predecessors.

What existing surveys already organize

Recent surveys provide several useful organizing perspectives. Broad GUI surveys cover data, architectures, training, evaluation, and applications; platform-focused reviews explain the constraints of browser or phone interaction; specialized reviews examine trust and efficiency. Table 1 compares the documented emphasis of eight surveys whose relevant full-text sections were inspected for this discussion. The entries describe their organizing choices, not exclusive coverage boundaries. A topic not named in a cell should not be interpreted as absent from that survey. The versions matter: several first appeared in 2024 or 2025 and were subsequently revised, so the comparison refers to the identified revision rather than assuming a fixed publication-year snapshot.

These perspectives overlap productively. Data and benchmarks are already central to broad GUI reviews, while operational concerns also appear in platform surveys. Trust and efficiency are not independent afterthoughts: verification can introduce runtime cost, and a successful sequence may still have unacceptable side effects. The trustworthy-GUI survey examines this through the relationship between perception, reasoning, and interaction; the efficiency survey follows resource use across the same loop. Our emphasis is to make the connection from a research statement to its supporting artifact and evaluation setting explicit.

That emphasis changes the questions asked of a contribution. A released repository may contain an agent, a dataset, an evaluator, or several components with different versions and permissions. A dataset paper and a later distribution can describe the same research lineage without identifying the same bytes. An environment may support multiple operating systems while a particular experiment covers only one. Accordingly, the later sections distinguish paper-level contributions from artifact-level properties and attach claims to the relevant setting. This is a complementary reading of the literature, intended to help readers identify what can be learned, tested, or reused from a work without inferring guarantees from its name or its presence in a catalog.

How this section was read

This section is an evidence-traced narrative synthesis. All 15 survey records in the frozen inventory received primary-page metadata and abstract checks; eight were selected for deeper comparison. Relevant sections of those eight surveys and 12 foundational papers were read in retained primary HTML or PDF. Sikuli's narrower historical description uses its complete institutional abstract and author project page; the linked full paper was unavailable during retrieval. These reading statuses are recorded separately from catalog inclusion. The inventory is a discovery aid.
