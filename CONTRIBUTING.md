# Contributing

Contributions should improve coverage or trustworthiness. A small correction with primary evidence is valuable.

Report security vulnerabilities privately, as described in [SECURITY.md](SECURITY.md), never in a public issue.

1. Search `data/catalog.jsonl` and `data/candidates.jsonl` for existing IDs, aliases, and mirrors. [Editorial input](docs/editorial-input.md#resource-id) shows how a URL maps to its ID.
2. Add an editorial proposal to `data/editorial.json` with `name`, `kind`, the primary `url`, `environments`, `topics`, a concise original `summary`, `verify_terms`, and `editorial_reviewed: false`. [Editorial input](docs/editorial-input.md) documents every key, its default, and its effect on the published record.
3. Run `python3 scripts/catalog.py verify --id <id>` with the proposal's [ID](docs/editorial-input.md#resource-id) and inspect the actual primary source. `--id` can be repeated; it fetches only the named entries, leaves every other receipt in `data/primary-evidence.jsonl` unchanged, and rejects an ID that no editorial entry has. Without it, `verify` refetches every entry. HTTP status or keyword presence is not enough. Check scope, current naming, and the exact asset being described.
4. After review, set `editorial_reviewed: true` and copy `reviewed_sha256` from the matching receipt in `data/primary-evidence.jsonl`. Record the UTC review time in `reviewed_at`; it is informational and only orders the README's recently reviewed list. Keep unresolved proposals unapproved with a `review_note`.
5. Regenerate views with `python3 scripts/catalog.py enrich --id <id>` and `python3 scripts/catalog.py build`. `python3 scripts/catalog.py lint` lists curated summaries over 220 characters, non-paper summaries under 60 characters, and summaries without a terminal period or with superlatives; its report is advisory and never fails. Then run every command in [Maintain and verify](README.md#maintain-and-verify), which match the CI checks: `validate`, `build --check`, the Python tests, the Node.js web tests, and the website build.
6. Submit the source changes and generated views together. Explain the evidence, any uncertain facts, and whether the resource is core or adjacent.

Do not directly edit generated files. [Authored and generated files](docs/data-dictionary.md#authored-and-generated-files) lists every input and the command that writes each output. Do not copy upstream abstracts, READMEs, datasets, or model weights into this repository. Do not infer dataset/model licensing from the code license. Preserve unknowns as null, with count units and evaluation settings stated when facts are available.

To resolve a discovered candidate without curating it, add an entry to `data/candidate-reviews.json` after inspecting its primary page: `not_a_resource` for a badge, file or placeholder, `alias` with `target_id` for another address of an active record, or `out_of_scope` for a GitHub, Hugging Face or website resource outside the computer-use scope. An `out_of_scope` entry names one `id` and `url` (no `url_prefix`) and needs a specific `reason`, `reviewed_at`, and an `evidence` receipt with the page's `url`, `sha256` and `retrieved_at`; the build rejects it otherwise. Out-of-scope arXiv papers go in `data/exclusions.json` as described in [scope review](docs/scope-review.md). [Methodology](docs/methodology.md#explicit-scope-review) explains each decision.

New discovery sources belong in `data/sources.json`. Identify the exact document and scope; prefer complementary sources over mirrors. Do not promote a list entry to a curated record without a first-party check. Report broken links, missing resources, and incorrect merges through the issue template.

## Resolving conflicts with the scheduled scan

The scheduled scan commits regenerated data and views to `main` three times a day, so a pull request that commits generated files will often conflict. Rebase onto `main` (`git fetch origin && git rebase origin/main`). Resolve conflicts in authored files by hand. For a conflicting build output or scan-written file, take `main`'s version (`git checkout origin/main -- <path>`) instead of merging it. If that drops your own `verify` or `enrich` results, rerun those commands. Then run `python3 scripts/catalog.py build` to regenerate the build outputs from the combined sources, confirm `python3 scripts/catalog.py build --check` passes, stage the result, and continue the rebase.
